# Contributing — SkyLine

Спасибо, что хотите внести вклад в проект SkyLine! Этот документ описывает
процесс разработки и правила для контрибьюторов.

---

## Как сообщить о баге

1. Проверьте, не описан ли баг уже в [Issues](https://github.com/BASH-Site/skyline-bashkortostan/issues).
2. Если баг новый — откройте новый Issue с шаблоном:
   - **Заголовок:** кратко, что не работает (например, «Калькулятор не считает скидку при площади > 100 м²»)
   - **Шаги для воспроизведения:** нумерованный список действий
   - **Ожидаемый результат:** что должно было произойти
   - **Фактический результат:** что произошло
   - **Окружение:** браузер, версия, ОС, устройство (десктоп/мобайл)
   - **Скриншот/видео:** если применимо
3. Не закрывайте Issue сами — дождитесь ответа мейнтейнера.

---

## Как предложить улучшение (Feature Request)

1. Откройте Issue с пометкой `[Feature]` в заголовке.
2. Опишите:
   - **Проблему:** какую пользовательскую задачу решает фича
   - **Предложенное решение:** как вы видите реализацию
   - **Альтернативы:** какие ещё варианты рассматривали
   - **Мотивация:** почему это важно для проекта
3. Дождитесь обсуждения с мейнтейнером. Не начинайте кодить фичу без одобрения —
   чтобы не тратить время впустую.

---

## Как сделать Pull Request

1. Сделайте fork репозитория.
2. Создайте ветку от `main`:
   ```bash
   git checkout -b feature/short-description
   # или
   git checkout -b fix/short-description
   ```
3. Внесите изменения. Коммитьте часто, маленькими порциями.
4. Убедитесь, что:
   - HTML валиден (прогон через [W3C Validator](https://validator.w3.org/))
   - Нет эмодзи в коде и контенте (правило проекта)
   - WCAG 2.1 AA не нарушен (проверьте фокус, контраст, ARIA)
   - Мобильная вёрстка не сломана
   - CSP не нарушен (если добавляете inline-скрипты — нужен nonce)
5. Сделайте коммиты в стиле [Conventional Commits](https://www.conventionalcommits.org/):
   ```
   feat(calculator): add discount for area > 100 m²
   fix(hero): correct glassmorphism blur in Safari 15
   docs(readme): update deploy section
   chore(deps): bump dependencies
   ```
6. Запушьте ветку и откройте PR в `main`.
7. В описании PR укажите:
   - Что изменилось и зачем
   - Ссылку на Issue (если есть): `Closes #123`
   - Скриншоты до/после (для UI-изменений)

## Стиль кода

### Общие правила

- **Отступы:** 2 пробела (не табы!)
- **Кодировка:** UTF-8 без BOM
- **Перенос строк:** LF (Unix), не CRLF
- **Конец файла:** одна пустая строка в конце
- **Длина строки:** мягкий лимит 120 символов, жёсткий — 180
- **Без эмодзи:** в коде, комментариях, контенте. Используйте SVG-иконки или текст.

### HTML

- Semantic HTML5: `<header>`, `<main>`, `<section>`, `<article>`, `<aside>`, `<footer>`, `<nav>`
- Один H1 на страницу, иерархия H2 → H3 → H4 без пропусков
- Все изображения — с `alt` (описательный для контентных, пустой для декоративных)
- Все интерактивные элементы — с `aria-label`, если текста недостаточно
- Формы — с `<label>`, `aria-required`, `aria-invalid`, `aria-describedby`
- Кнопки — `<button>`, ссылки — `<a>`. Не путать.
- Без inline-стилей (только для критичного CSS в `<head>`)
- Inline-скрипты — только с `nonce`. Лучше — external файл.

### CSS

- Custom properties (переменные) в `:root` для цветов, отступов, шрифтов
- Mobile-first: базовые стили для мобайл, медиа-запросы `min-width` для больших экранов
- `clamp()` для адаптивной типографики
- `:focus-visible` вместо `:focus` для стилизации фокуса
- Контраст текста ≥ 4.5:1 (WCAG AA)
- Без `!important` (кроме редких исключений — обосновать в комментарии)
- BEM-нейминг или каскад по смыслу — на ваш выбор, но консистентно в рамках компонента

### JavaScript

- Vanilla JS (ES6+), без фреймворков и jQuery
- `const` по умолчанию, `let` только когда нужно переназначать, без `var`
- Стрелочные функции для колбеков, обычные для методов класса
- `async/await` вместо `.then()` где возможно
- Optional chaining `?.` и nullish coalescing `??` — можно
- Strict mode: `'use strict';` или модули `type="module"`
- Без `eval`, `new Function()`, `innerHTML` (CSP strict это заблокирует)
  - Используйте `textContent`, `createElement`, `insertAdjacentHTML` с санитизацией
- Все обработчики — addEventListener, не `onclick=` атрибуты
- Дебаунс для scroll/resize (rAF или lodash-подобный debounce)

### PHP (для backend)

- Strict types: `declare(strict_types=1);` в начале каждого файла
- Type hints для параметров и return types
- PDO с подготовленными запросами, без конкатенации SQL
- `htmlspecialchars($val, ENT_QUOTES | ENT_HTML5, 'UTF-8')` для вывода в HTML
- Никаких секретов в коде — только в `.env` / `config.php` (в `.gitignore`)

## Проверка перед PR

- [ ] HTML валиден (W3C)
- [ ] CSS проходит автопрефиксер (если добавляете новые свойства)
- [ ] JS без ошибок в консоли (Chrome + Firefox)
- [ ] Lighthouse: Performance ≥ 90, Accessibility ≥ 95, SEO ≥ 95, Best Practices ≥ 95
- [ ] Мобильная вёрстка: 320px, 375px, 414px, 768px, 1024px, 1440px
- [ ] WCAG 2.1 AA: фокус, контраст, ARIA, клавиатура
- [ ] Нет эмодзи в коде и контенте
- [ ] CSP не нарушен (если добавляли inline — нужен nonce)
- [ ] Тест в тёмной теме
- [ ] Тест в Safari (если есть доступ)

## Процесс ревью

1. PR рассматривается в течение 2-3 рабочих дней.
2. Мейнтейнер может запросить изменения — не расстраивайтесь, это нормально.
3. После аппрува — squash & merge в `main`.
4. После мерджа — изменения попадут в следующий релиз (см. [CHANGELOG.md](CHANGELOG.md)).
